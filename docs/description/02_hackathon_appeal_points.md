# Rakufuku（ラクフク）ハッカソン・アピールポイント分析

> 対象: 第4回 Agentic AI Hackathon with Google Cloud

---

## 1. 公式審査基準と戦略

### 審査基準（公式3軸）

| 評価軸 | 審査員が見ているポイント | Rakufukuの強み |
|--------|------------------------|---------------|
| **課題の新規性** | 多くの人が抱える未解決の問題を発見したか | 「毎朝の服選び」は全人類共通の課題。既存AIでは解決できていない |
| **解決策の有効性** | 課題に効果的に対処し、解決しているか | 4人のAIスタイリストが天気・予定・好みを統合して実際に使えるコーデを提案 |
| **実装品質と拡張性** | 実現度、ツール活用、拡張性、運用性、費用対効果 | Google Cloud技術6種統合、多層フォールバック、日次キャッシュ、Tier管理 |

### 審査の特徴

- **段階審査**: 1次（2/16-23）→ 2次（2/24-3/2）→ 最終（3/19）
- **奨励賞5枠新設**: 「課題発見」「アイデア」「実装」の**どこかが光っていれば受賞できる**
- **Agentic AI**: 自律的に考え行動するAIであることが前提テーマ

### 必須要件チェック

| 必須要件 | 充足状況 |
|---------|---------|
| Google Cloud実行プロダクト1つ以上 | **Cloud Run**（バックエンドAPI実行環境） |
| Google Cloud AI技術1つ以上 | **Gemini 2.0 Flash** / **Gemini 2.5 Flash** / **Imagen 4 Fast** / **Cloud Vision API**（4技術使用） |
| 自律的に考え行動するAIエージェント | 4つの専門スタイルエージェントが独立したペルソナで自律的にコーデ生成 + オーケストレーターが統合判断 |

### 勝ち筋

Rakufukuは3軸全てでアピールできるが、特に**「課題の新規性」×「解決策の有効性」**の掛け算が最大の武器。「誰もが共感する課題」を「マルチエージェントで本質的に解決」している点が差別化の核心。

## 2. 審査軸別アピールポイント

### 軸1: 課題の新規性 ── 「毎朝の10分」という全人類の未解決問題

**課題の定義**

> 毎朝、天気を調べ、今日の予定を確認し、クローゼットを眺めて「何を着ればいいか」悩む。この意思決定に平均10分。年間60時間。しかもその結果に自信が持てない。

**なぜ未解決なのか**

- **既存ファッションAI（ChatGPT等）**: ユーザーが天気・予定・手持ち服を毎回テキストで説明する必要がある。面倒で続かない
- **コーデアプリ（WEAR等）**: 他人のコーデを見るだけ。自分の手持ち服・体型・予定とは無関係
- **スタイリストサービス**: 高額（月数万円）で一般に使えない

**Rakufukuが発見した課題の本質**

服選びの困難さは「センスがない」ことではなく、**天気・予定・手持ち服・好みという4つの変数を同時に最適化する認知負荷の高さ**にある。これは人間の脳が苦手な多変数最適化問題であり、AIエージェントが最も得意とする領域。

**30秒ピッチ**

> 「毎朝10分、服選びに悩んでいませんか？天気を見て、予定を確認して、クローゼットを眺めて……。この"朝の意思決定地獄"は全人類共通の課題です。でも既存のAIは、毎回あなたの状況を説明しないと使えない。Rakufukuは天気も予定も好みも全部自動で把握して、あなた専用のコーデを毎朝AIが選びます。」

---

### 軸2: 解決策の有効性 ── 4人のAIスタイリストチームが本質的に課題を解く

**解決策の全体像**

Rakufukuは「1つのAIに聞く」のではなく、**4人の専門AIスタイリストがチームで考え、オーケストレーターが最適解を選ぶ**マルチエージェントシステム。人間のスタイリストチームの働き方をAIで再現した。

**なぜ有効なのか ── 3つの理由**

#### 理由1: マルチエージェントによる多角的提案

単一AIは「平均的な1つの回答」しか出せない。Rakufukuの4エージェントは**意図的に異なる方向の提案**を生成する:

```
CasualAgent   → 「デニムにスニーカーでリラックス!」
FormalAgent   → 「ジャケットにレザーシューズで好印象」
BalancedAgent → 「キレイめカジュアルで万能に」
UniqueAgent   → 「2026年トレンドのラベンダーで差をつけよう」
    ↓
Orchestrator  → 天気×予定×好み でスコアリング → 最適5着をランキング
```

各エージェントは独自のペルソナ・カラーパレット・スタイル哲学を持つ。単なるプロンプトの分岐ではなく、本質的に異なる「思考」をする。

#### 理由2: コンテキスト自動統合で「毎回説明」が不要

```
天気API（OpenWeather）       → 気温22℃、晴れ → 軽めのアウター推奨
カレンダーAPI（Google）      → 14時に商談 → フォーマリティ: business_casual
クローゼット（Firestore）    → 手持ち47アイテムから選定
嗜好プロファイル（学習済み）  → カジュアル好み、ネイビー多用
ユーザー情報                  → 男性
    ↓
5データソースを自動統合 → 4エージェントに同時供給
```

ユーザーは**アプリを開くだけ**。天気も予定もクローゼットも全部AIが自動で把握する。

#### 理由3: 使うほど精度が上がる嗜好学習

提案コーデを「いいね / パス」するだけで、AIが好みを学習（EMA: 指数移動平均）。アンケート不要。TikTokやSpotifyと同じ暗黙的フィードバック設計。

- スタイルスコア: casual/formal/balanced/uniqueの4次元
- カラー嗜好: 色ごとの好みスコア
- フォーマリティ分布: 普段着のドレスコード傾向

**課題解決の完全性**

| 課題の要素 | 既存AIの対応 | Rakufukuの対応 |
|-----------|-------------|---------------|
| 天気を調べる | ユーザーが手動入力 | OpenWeather APIで自動取得 |
| 予定を確認する | ユーザーが手動入力 | Google Calendar APIで自動取得・TPO判定 |
| クローゼットを眺める | 対応なし | 写真1枚でCV自動登録、手持ち全アイテム参照 |
| 好みに合うか考える | 毎回説明し直す | スワイプ学習で自動把握 |
| コーデを組む | 1パターンだけ提案 | 4エージェントが5パターン提案 |
| 似合うかイメージする | テキストのみ | Imagen 4 Fastでマネキン画像生成 |
| 不足アイテムを買う | 対応なし | 楽天/Amazon/ZOZOTOWNリンク自動生成 |

**30秒ピッチ**

> 「Rakufukuには4人のAIスタイリストがいます。カジュアル派、フォーマル派、バランス派、トレンド派。彼らはクローゼット・天気・予定・好みを全部把握した上で、並列でコーデを考えます。オーケストレーターAIが全提案をスコアリングし、最適な5着を選出。スワイプするだけで好みを学習し、使うほど精度が上がります。」

---

### 軸3: 実装品質と拡張性 ── Google Cloud技術6種をフル活用

**Google Cloud技術の活用一覧**

| Google Cloud技術 | 用途 | 実装ファイル |
|-----------------|------|------------|
| **Gemini 2.0 Flash**（Vertex AI） | コーデ生成（4エージェントの思考エンジン） | `gemini_outfit_composer.py` |
| **Gemini 2.5 Flash**（Vertex AI） | コーデ診断・評価・アイテム詳細分析 | `outfit_analyzer.py` |
| **Imagen 4 Fast**（Vertex AI） | マネキン画像生成 | `nano_banana.py` |
| **Cloud Vision API** | 物体検出（服飾アイテムの位置特定） | `outfit_analyzer.py` |
| **Cloud Run** | バックエンドAPI実行環境 | デプロイ構成 |
| **Firebase**（Firestore / Cloud Storage / Auth） | データ永続化・画像保存・認証 | 全ツール |

**実装品質を示す設計**

#### 多層フォールバック戦略

全てのAI機能に「失敗しても動く」設計を実装:

| 障害シナリオ | フォールバック |
|-------------|--------------|
| Gemini応答失敗 | 決定論的ルールベース選定（各エージェント独立） |
| Imagen画像生成失敗 | フロントエンドのプレースホルダー表示 |
| Cloud Vision失敗 | Gemini Visionで物体検出を代替 |
| 天気API失敗 | デフォルト天気（20℃、晴れ） |
| Calendar API失敗 | デフォルトTPO（casual） |
| 楽天API失敗 | アフィリエイトリンクのみ |
| Firebase Storage失敗 | ローカルプレースホルダー |
| 全エージェント失敗 | 最低1着は決定論的に保証 |

#### パフォーマンス設計

- **4エージェント完全並列実行**: `asyncio.gather()`で同時処理
- **日次キャッシュ**: 同日の再リクエストはFirestoreキャッシュから即時返却
- **Tier管理**: Free/Premium の生成回数制限（将来のマネタイズ設計済み）

#### 拡張性

- **エージェント追加が容易**: `BaseStyleAgent`を継承して新スタイルエージェントを追加可能
- **ツール追加が容易**: 新しいデータソース（例: 体型分析、色診断）を`tools/`に追加してオーケストレーターに接続
- **ADK設計パターン準拠**: `adk_config.py`でGoogle Agent Development Kitの設計パターンを参考に設定共有（ランタイム実行ではなく設定管理として統合）
- **費用対効果**: Gemini Flash（低コスト高速モデル）を採用。Imagen 4 Fastも高速版を選択

**30秒ピッチ**

> 「Rakufukuは Google Cloud の AI 技術6種をフル活用しています。Gemini Flash がコーデを考え、Imagen 4 Fast が画像を生成し、Cloud Vision が服を認識する。Cloud Run上で4エージェントが並列実行し、Firebase でデータを永続化。全AI機能にフォールバックを実装し、1つが落ちても止まらない。Gemini Flashの低コスト高速推論で費用対効果も確保。デモではなく、本番運用を見据えた設計です。」

## 3. 統合アピール戦略

### 「一言で伝わる」キーフレーズ

#### 最強の一言（審査全軸カバー）

> **「毎朝の服選びを、4人のAIスタイリストチームが解決する」**

この一文で3軸全てを示唆:
- 課題の新規性: 「毎朝の服選び」（誰もが共感する未解決課題）
- 解決策の有効性: 「4人のAIスタイリストチーム」（マルチエージェントで本質的に解決）
- 実装品質: 「チーム」（オーケストレーター統合を暗示）

#### 審査軸別フレーズ

| 軸 | フレーズ |
|----|---------|
| 課題の新規性 | 「毎朝10分、年間60時間。全人類が服選びに費やす時間をAIでゼロにする」 |

#### 技術者向け

- 「asyncio.gatherで4エージェント完全並列 + diversity guaranteeでスタイル多様性を保証」

## 4. 競合との差別化

### 一般的なファッションAI vs Rakufuku

| 観点 | ChatGPT + プロンプト | Rakufuku |
|------|---------------------|----------|
| アーキテクチャ | 1つのLLMにプロンプトを投げるだけ | 4エージェント並列 + オーケストレーター統合 |
| コンテキスト | ユーザーが毎回手動入力 | 天気API・Calendar APIから自動取得 |
| パーソナライズ | 毎回同じ質問に答える | スワイプ行動からEMAで暗黙学習 |
| クローゼット連携 | なし（想像で提案） | 実際の手持ちアイテムから選定 |
| 可視化 | テキストのみ | Imagen 4 Fastでフォトリアル画像生成 |
| アイテム登録 | 手動入力 | 写真1枚 → CV自動認識 → クロップ → 登録 |
| 不足アイテム | 対応なし | 楽天/Amazon/ZOZOTOWNの購入リンク自動生成 |
| 堅牢性 | LLM失敗 → エラー | 全ツールに多層フォールバック |
| Google Cloud活用 | API 1つ | 6技術統合（Gemini 2.0 Flash, Gemini 2.5 Flash, Imagen 4 Fast, Cloud Vision, Cloud Run, Firebase） |

### エンドツーエンドの完成度

Rakufukuは「写真を撮る → クローゼット登録 → 毎朝コーデ提案 → スワイプで学習 → 精度向上」というユーザージャーニー全体をカバー。「1機能だけ動くデモ」ではなく、日常使いできるプロダクトレベルの完成度。

## 5. デモ戦略

### 限られた時間で最大インパクトを出す順序

#### 最初の30秒: 課題共感（審査軸1）

「毎朝10分、服選びに悩んだことありませんか？」
→ 聴衆がうなずく

#### 次の60秒: 動くプロダクトを見せる（審査軸2）

| 順序 | デモ内容 | 見せるポイント | 時間 |
|------|---------|---------------|------|
| 1 | 「今日のコーデ」画面を開く | マネキン画像付き5着提案。天気・予定が自動反映 | 20秒 |
| 2 | コーデカードをスワイプ | 4エージェントの異なるスタイル提案を見比べ | 20秒 |
| 3 | 1着選んで詳細表示 | AIの推薦理由、不足アイテムの購入リンク | 20秒 |

#### 次の60秒: 技術解説（審査軸3）

| 順序 | デモ内容 | 見せるポイント | 時間 |
|------|---------|---------------|------|
| 4 | アーキテクチャ図1枚 | 4エージェント並列 → オーケストレーター統合の全体像 | 30秒 |
| 5 | Google Cloud技術一覧 | 6技術の活用箇所を一覧表示 | 30秒 |

#### 残り時間: 追加デモ

| 優先度 | デモ内容 | アピール軸 |
|--------|---------|-----------|
| 高 | 写真撮影 → CV自動認識 → クローゼット登録 | 解決策の有効性 |
| 高 | スワイプ → 嗜好学習の説明 | 解決策の有効性 |
| 中 | フォールバック設計の説明 | 実装品質 |
| 中 | ADK設計パターン準拠の説明 | 実装品質・拡張性 |

### デモの鉄則

1. **最初の30秒で課題共感** → 技術説明から入らない
2. **動くプロダクトを先に見せる** → アーキテクチャ図は後
3. **「4人のAIスタイリスト」を繰り返す** → 記憶に残るメタファー
4. **Google Cloud技術名を明示的に言う** → 審査要件の充足を示す
5. **「デモではなく本番品質」を強調** → フォールバック・キャッシュに言及

## 6. 奨励賞を狙う場合の特化戦略

公式: 「課題発見」「アイデア」「実装」のどこかが光っていれば受賞できる

| 賞の方向性 | 特化アピール |
|-----------|-------------|
| **課題発見賞** | 「毎朝の服選び = 多変数最適化問題」という課題定義の鋭さ。天気×予定×好み×手持ち服の4変数を同時最適化するのは人間の脳が苦手でAIが得意、という洞察。**訴求ポイント**: 既存AIとの差を「4変数同時最適化」で端的に表現 |
| **アイデア賞** | 「4人のAIスタイリストチーム」という擬人化設計。単一AIではなくマルチエージェントで多角的提案→オーケストレーター統合というアーキテクチャの着想。**訴求ポイント**: 人間のスタイリストチームの働き方をAIで再現した「メタファー駆動設計」 |
| **実装賞** | Google Cloud 6技術統合、全機能フォールバック、4エージェント並列実行、EMA嗜好学習、4段CVパイプライン。**訴求ポイント**: 全7コンポーネントに独立フォールバック実装 + Gemini Flash採用による費用対効果の両立 |
